This is a test repository for README to Landing Page, a GitHub Action that converts a README.md into a static site and deploys it to GitHub Pages. The action lives in that project; this repo only consumes bmoler68/readme-to-landing-page@v1 so the conversion and Pages publish can be checked end to end.

The generated landing page is at bmoler68.github.io/README-2-landing-page-test. It is rebuilt on each push to main by .github/workflows/landing-page.yml. If the site is missing, enable Pages on the gh-pages branch at / (root) after the first successful workflow run.

The action itself needs no local CLI: add a workflow in any target repository. Project homepage: brianmoler.com.

How it works

README.md → parse → generate site → push gh-pages → GitHub Pages

The action runs as a Docker container (action.yml → Dockerfile). At runtime it:

  1. Parses the README with marked (GFM). The first H1 becomes the page title. Badge images immediately after that heading become the hero badge row. A TOC is built from H2 and H3 when include-toc is not 'false'.
  2. Generates index.html and styles.css from templates. HTML is passed through sanitize-html.
  3. Publishes only the generated site to the gh-pages branch using GITHUB_TOKEN. The source branch (main) is not rewritten.

Add the workflow

In the target repository (the project whose README should become a landing page), create .github/workflows/landing-page.yml:

name: Build Landing Page

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: bmoler68/readme-to-landing-page@v1

Do not create a gh-pages branch yourself, and do not point GitHub Pages at main. The action publishes a complete static site to the root of gh-pages. Using main (either / (root) or /docs) would serve the source repo instead of the landing page or get overwritten.

Configure with `with:`

The step that uses this action can take optional with: keys. Omit with: entirely to use the defaults (root README.md, publish to gh-pages, include a table of contents).

      - uses: bmoler68/readme-to-landing-page@v1
        with:
          readme-path: README.md
          output-dir: site
          branch: gh-pages
          include-toc: 'true'
          github-token: ${{ secrets.GITHUB_TOKEN }}
InputDescriptionDefault
readme-pathPath to the README, relative to the repository rootREADME.md
output-dirWorking directory for generated files before they are pushedsite
branchBranch that receives the published sitegh-pages
include-tocWhether the generated page includes a table of contents (true / false)true
github-tokenToken used to push to the publish branch${{ github.token }}

YAML treats true/false as booleans. Quote them ('true', 'false') so GitHub Actions receives the string the action expects.

You only need github-token if you are not using the default GITHUB_TOKEN. The workflow still needs permissions: contents: write so the token can push.

Example: README in a subdirectory, no table of contents:

      - uses: bmoler68/readme-to-landing-page@v1
        with:
          readme-path: docs/README.md
          include-toc: 'false'

Enable GitHub Pages

Until gh-pages exists, Settings → Pages will only list branches that already exist (usually None and main). That is expected.

  1. Leave Pages set to None (or skip Pages until after the first successful run).
  2. Add the workflow and run it once (push to main, or Actions → Run workflow).
  3. The action creates gh-pages if it is missing and pushes index.html, styles.css, and assets/ to that branch. Your main branch is not changed.
  4. Return to Settings → Pages, choose Deploy from a branch, then gh-pages and / (root). Refresh the page if gh-pages is not in the list yet.

After that, each push to main updates gh-pages, and GitHub Pages serves the generated site.
